Programming
Welcome to the Elevator Challenge! This assignment will immerse you in a classic AI planning
problem set in the bustling environment of a high-rise building during the evening rush hour. Your
mission, should you choose to accept it, is to design and implement planning solutions for a single
elevator serving passengers with different start and destination floors. This seemingly simple sce-
nario brings a host of planning challenges involving state modelling, capacity constraints, ordering,
and service quality.

Background: The Elevator Domain
The Elevator Domain is a well-known problem in AI planning that captures the intricacies of
coordinating movements in a constrained environment. Imagine a busy office building with several
floors and passengers travelling between different parts of the building. There is ONLY ONE
elevator, but its capacity is specified by each problem configuration. The elevator can start from
any floor and may need to make several trips to serve all passengers while respecting its door and
occupancy constraints.
    For more insight into the elevator’s operation, please explore the provided interactive Jupyter
notebook, 0 env walkthrough.ipynb, where you can play around with different scenarios
and understand the domain constraints and dynamics in detail.

Programming Solution Sketches
Problem 1: Classical Planning
In the first task, you will implement a solution using the Planning Domain Definition Language
(PDDL), a standard language for expressing planning problems. You will model the elevator do-
main by defining the relevant objects, states, actions, and goals. The model should support pas-
sengers traveling between arbitrary floors and will be extended to represent a configurable elevator
capacity.

    Solution:
 To approach the elevator problem in PDDL, consider the following components.
1. Domain File:

    • The types and predicates are predefined and fixed, do not add, delete, or rename predicates
      and parameters.

    • The movement, door, loading, and unloading actions should use preconditions and effects
      that preserve the intended elevator rules. For each action, identify which facts must hold for
      it to be legal and which facts it makes true and false. Delete effects matter as much as add
      effects: a fact that is no longer true must be retracted.

    • In the capacity-aware model, also represent passenger destinations, completed trips, and the
      current number of passengers in the elevator.

2. Problem File:

    • Generate the objects, initial state, and goals from the supplied configuration rather than
      assuming fixed passenger locations or destinations.

    • Include both directions of floor adjacency and initialise the elevator at the configured floor.

    • In the capacity-aware problem, initialise the count chain and correctly handle passengers
      who are already at their destinations.

3. Verification:

    • Run the planner on several configurations and inspect the meaning of the returned actions.

    • Planner success shows that a plan is valid under your model; it does not by itself show that
      the model matches the intended domain.
    • Hidden tests use the documented configuration schemas, so the implementation should gen-
      eralise beyond the notebook examples.
   You May Want to Pay Attention To:
    • The elevator should move only when its door is closed.
    • Loading and unloading should require the correct passenger and elevator locations and
      should update occupancy consistently.
    • When the elevator reaches full, it should be unable to load because the count chain has
      no step beyond the capacity. In addition, a delivered passenger should never board again.
      Remember to check for boundary cases.
    • AI-generated PDDL should be treated as a draft and checked against the domain rules. The
      optional AI-audit notes field may be left blank and is not read by the autograder; prompt
      transcripts are not graded.

Problem 2: Hierarchical Planning
Hierarchical Task Network (HTN) planning breaks complex tasks into simpler subtasks. In the
second task, you will create a hierarchical model for the same elevator domain, specifying primi-
tive actions, abstract tasks, methods, and an ordered task network while preserving the destination
and capacity constraints from Problem 1.

   Solution:

The provided code includes the following:
Objects: Floor, Elevator, Person, and Count, which describe the objects used by the fixed repre-
sentation.

Fluents: Fluents track passenger and elevator locations, the door state, passenger destinations and
completion, and the elevator occupancy count.

Actions: move elevator, load, unload, open door, and close door. Their preconditions and effects
should preserve the same movement, door, destination, and capacity rules as in Problem 1.

Tasks and Methods: Pickup and delivery tasks require different decompositions depending on
whether the elevator is already at the relevant floor. A separate case handles passengers who begin
at their destination and need no subtasks. The primitive subtasks within each method must be to-
tally ordered.
Rush Hour Adventures: Episode I - AI Planning for the Elevator Challenge                               7


Initial Task Network: The service order is divided into consecutive capacity-sized batches after
initially reached passengers are filtered out. Add all pickups in a batch before its deliveries, and
totally order the complete task network.

Service Policy: Each request includes a deadline, base utility, and late penalty. The policy should
return every passenger index exactly once and seek high total utility. Completion time and elevator
travel are useful diagnostics, but only total utility contributes to the quality score. Test both service
quality and performance on the range of instances described in the notebook.

A successful planner result should also be checked against the intended primitive action sequence
and external timing model. The grader performs this replay independently. Package usage exam-
ples are available in the Unified Planning documentation.

Problem 3: Free-form Planning (Optional Bonus)
Problem 3 retains Problem 2’s passenger schema, capacity batching, timing rules, and utility eval-
uator but does not require actions, methods, or a task network. It uses larger instances and a hard
two-second limit for each case.

   Solution:

Implement a function that returns a permutation of all passenger indices. Initially completed pas-
sengers must remain in the returned permutation, although they are removed before the active
passengers are divided into capacity-sized batches. The external evaluator, rather than the submit-
ted module, determines completion times and total utility.

Any finite search or optimisation method may be used. A useful progression is to begin with ex-
haustive DFS, obtain a good incumbent early, and then consider branch-and-bound or dynamic
programming. When reusing partial results, make sure the stored state contains enough informa-
tion to determine the cost and utility of all future batches.

Test the policy across the published passenger-count ranges, including capacity one, partial final
batches, and initially completed passengers. Across twenty equally weighted hidden cases, each
case requires at least 98% of the optimal total utility within the hard two-second limit; runtime
below that limit is not itself a scoring objective.
