## 0. Terms used in this document (read first)

**Ply.** One move by one side. 99 plies is 49 full moves plus White's 50th.

**Stockfish depth N, written SF-dN.** The `depth` argument of a Stockfish call that scores ONE board and
returns centipawns, converted to a value in [-1, 1] by tanh(cp/600). SF-d1 is a few milliseconds a board
(about 2 ms on the VM); SF-d8 is 80 ms on the VM and 138 ms on Atlas. This is a property of the leaf
evaluator, never of our search.

**Subgame tree depth, in plies.** How far OUR search looks ahead from the current position. Set by
`AnytimeConfig(initial_depth=1, max_depth=2)` in `pair_a_prep/anytime_agent.py`: the tree is built one ply
deep and may grow to two. The Obscuro paper reports an average of 10.7 plies (`handover/notes/obscuro-vs-ours.md`).

**Belief.** Everything the agent believes about the hidden enemy position at one turn. Three distinct objects:
- *population*: every move history consistent with what the agent has observed, kept by the exact tracker
  (`BeliefTracker`, `pair_a_prep/belief_tracker.py`); can be in the billions.
- *sampled hypotheses*, or *hypothesis boards*: the boards the tracker hands to the search, drawn uniformly at
  random from the population, 16 of them (`sample_size = 16`), each with weight 1/16 (`_make_belief`). When
  the population is 16 or fewer, all of it.
- *belief marginals*: for each square and enemy piece type, the share of the 16 sampled hypotheses that put
  that piece there. Planes 14-19 of the network input, plus plane 20 (population size). They are marginals
  of the SAMPLE, not of the population.

**Exact tracker / guard tracker.** The exact tracker keeps the whole population. The guard tracker
(`guard_tracker:Factory`, `max_states = 96000`, "tail-guarded") prunes histories once the stored state count
passes 96,000. The label games used the guard setting (`MAX_STATES=96000` in the PBS scripts); the earlier
strength arms used the exact tracker on our side; the live head-to-head arm uses the guard tracker on both sides.

**Leaf evaluator, leaf.** The function the search calls when it stops looking ahead, to score a *frontier
board*. Three kinds exist: `material` (piece count), `stockfish` (SF-dN), `belief_network` (a trained
network, `pairb/belief_evaluator.py`). Today the search calls the leaf through `evaluate_children(fen)` on
ONE concrete board at a time (`pair_a_prep/chess_search.py:177`); the belief enters only at the root chance
node. See section 4.1.

**Record, solver label.** One record is one decision of the labelling agent: the agent input (observation plus
the 16 sampled hypotheses), the move, the solver's root policy, and the labels: `root_value` (the search's
value of the position) and `hypothesis_values` (one value per sampled board). "Solver label" always means
these search outputs. The leaf used inside that search is part of the record's `config_id`.

**Label round.** One Atlas collection. Round 1 used the material leaf (dataset `solver-v1`, superseded).
Round 2 = `labels-sf8`, PBS array 1038003[], SF-d8 leaf, 30 s per move, 240 games. Round 3 = `labels-sf8-r3`,
array 1038307[], same configuration, new seeds, running at the time of writing. Not to be confused with a
*PCFR+ round* (one iteration of the solver, hundreds per move) or a *chunk* (the two-game unit of a strength
arm).

**Datasets.** `solver-v2-sf8-mid` = the first 120 games of round 2 (midpoint). `solver-v2-sf8-g237` = 237 of
the 240 games (collected while the last three were still playing). `solver-v2-sf8` = all 240. `solver-v2-sf8-480`
= rounds 2 + 3, to be built when round 3 finishes. All split BY GAME with `pairb.data.split_of` (a hash of
the game id): 240 games -> 199 train / 25 validation / 16 test. The test split has never been read; it is
reserved for one final evaluation with `--final`.

**Validation metrics.** *Board error* = mean absolute error of the network's value against the hypothesis
value, over hypothesis boards, weighted by hypothesis weight, excluding boards the fog-of-war rules decide.
*Position error* = mean absolute error of the belief-weighted mean of the board values against `root_value`,
over records. Both on the 25 validation games (1,181 records, 17,868 boards, 17,518 not rule-decided).
Written as "board / position" below. `pairb/belief_eval.py`.

**Network v1 / network v2.** Network v1 = `belief-solver-v1`, trained on round-1 (material-leaf) labels, used
in the earlier `net-fe-s16` arm. Network v2 = any checkpoint trained on round-2 labels (`belief-solver-v2-sf8*`).
Both are Pair B's `BeliefNetwork` (D6) with the 32-plane encoder.

**Network input mode** (training/evaluation option `--input`, `pairb/belief_ablation.py`):
- `full`: every sampled hypothesis board with the 32 planes; the network as designed.
- `marginals`: ONE pseudo-board per record carrying the observation and the belief marginals, no sampled
  boards ("fuzzy board" in conversation).
- `observation`: one pseudo-board with the fogged observation only, hidden planes zero ("pure fog").
- `alone`, `alone-marginals` (evaluation only, "leaf mode"): every stored board scored as a belief of one,
  the way the search presents boards to the leaf today.

**Recipe v1 / v2.** v1 = Pair B's trainer defaults: AdamW lr 2e-3, weight decay 1e-4, 30 epochs, patience 5,
6 residual blocks x 64 channels, epoch chosen by validation board MSE. v2 = the same with lr 1e-3.

**Residual variant (closed).** `--use-d1`: the network reads SF-d1 of each board as an input and predicts a
correction to it. Closed on 2026-11-09 by the user's decision because the leaf then needs an engine call at
play time. Its one result is kept in section 2.7 as a record only; it must not be presented as a network-leaf result.

**Solver root policy / played policy / policy head.** The *solver root policy* (`decision.root_policy`) is
the PCFR+ last-iterate strategy over the observed legal moves. The *played policy* (`played_policy:<uci>`
diagnostics) is the purified policy the move was drawn from. The *policy head* is a network output that
predicts a move distribution (section 2.6, parked).

**Fallback / failed game.** A *fallback* is a move the labelling agent played uniformly at random after the
search raised `SearchBudgetError` or `TreeCapacityError`; no record is written for it. A *failed game* ended
with an exception; the records written before it are kept, and the error is in `progress.jsonl`.

**Strength arm, chunk.** An arm is one match configuration, run as 50 chunks of 2 games with fixed seeds
(seed 1001 + 2(N-1) for chunk N), 5 s per move, 200-ply cap, colours alternating. Score = (wins + draws/2) /
scored games; games that hit the ply cap or failed are excluded and counted separately.

## 2. Results

### 2.1 Round-two labels (`solver-v2-sf8`)

240 games, 11,679 records, 1,251 fallbacks (9.7 % of labelled-or-fallback moves), 16 failed games whose
partial records are kept (14 `BeliefBudgetError: no_candidate`, 2 `EngineTerminatedError`). Games average 64.5
plies. Configuration: SF-d8 leaf, 30 s per move, expansion fraction 0.85, 16 sampled hypotheses, guard tracker
at 96,000 states, 200-ply cap, 20 Atlas tasks x 12 games, seeds 50001 + 1000N + 2i. Wall time about 5 hours with
all 20 tasks running at once (NUSREC-HPC-00001).

Fallback cause: 92 % "budget exhausted during tree construction", i.e. building the first ply over 16 roots at
0.138 s per SF-d8 child evaluation exceeds the 30 s clock on wide positions. Fallbacks therefore bias the labels
against positions with many legal moves. Round 1 at the material leaf had 2.1 %.

Two failure modes fixed during the round: a Stockfish call exceeding the 10 s watchdog closed the engine for
good (`pairb/stockfish.py`) and every later game of the task died (`RevivingLeaf` fixes this; tasks 5 and 6 were
replayed); a 15 GB cgroup memory kill (task 13; resume fixes it). A resumed task exits 1 because the in-run
validator compares the parts against the stale first-run `manifest.json`; the data are complete.

### 2.6 Policy head (parked), `runs/belief-solver-v2-sf8-policy-pw{1.0,0.3}-lr1e-3`

Target statistics: 31 legal moves per position on average; the solver root policy is nearly deterministic,
mean entropy 0.39 nats (uniform over legal moves: 3.37), 58 % of positions put more than 0.9 on one move.
So the attainable cross-entropy is about 0.4.

| Run (240 games, lr 1e-3) | position error | policy cross-entropy | top-1 agreement |
|---|---|---|---|
| no policy head (recipe v2, 3 seeds) | 0.228-0.236 | uniform prior: 3.37 | uniform: about 0.03 |
| policy head, weight 1.0 | 0.281 | 3.23 | 0.18 |
| policy head, weight 0.3 | 0.258 | 3.28 | 0.16 |

Reading: sharing the trunk costs the value head 0.03-0.05; the head barely beats a uniform prior and overfits

### 2.9 Search scale, measured and from the paper (`handover/notes/obscuro-vs-ours.md`)

| | Obscuro | Ours |
|---|---|---|
| Subgame tree depth | 10.7 plies average | capped at 2 |
| Nodes per move | about 1.07 million | at most 16,384; about 1,200 in a 3.6 s move |
| Sampled roots | 256 | 16 |
| Leaf | SF-d1, one MultiPV call per expanded node | material / SF / network |
| 5 s clock covers | search only | search and belief tracking, one Python process |

About 330 nodes per second against roughly 200,000: interpreted Python on one core against compiled code on
five. Depth is cheap and breadth expensive: at today's speed 4-16 roots and 3-6 plies are reachable by raising
the cap; 256 roots are not (the earlier 256-root arm scored 0.042 because the tree could not be built).

Where a 5 s move goes (`$EXP/pipeline/profile_move.py`, three recorded positions replayed with the network v2
leaf, no tracker): the PCFR+ traversal (`pcfr.py` `_utilities`/`visit`, 4.5-7.7 million recursive calls per move)
31-51 % of the clock; python-chess move generation and board copies in construction and growth 15-27 %; the
network leaf, planes included, under 7 %. 900-1,400 nodes, 176-427 PCFR+ rounds, 19-66 growth steps per move,
no fallbacks. The leaf is not the bottleneck; the solver's Python traversal is.

## 4. Known defects and gaps

### 4.1 The network never sees a belief during play
`chess_search.py:177` calls `evaluator.evaluate_children(state.fen)` on one concrete board; the belief
evaluator wraps each board as a one-hypothesis belief (`_alone`). The marginal planes degenerate to
certainties and the context head sees one board. The network was trained on 16-board beliefs. Measured cost:
section 2.5.

Why this is not a small fix. With `initial_depth 1` every frontier board has the opponent to move, so the belief
a leaf board belongs to is the opponent's belief about us, which the tree does not represent: each sampled root
is a different opponent history, and grouping frontier boards by the opponent's information set gives groups of
one. Our own belief exists only at even plies (our-to-move leaves), which growth creates one root at a time, so
such a group changes while the tree grows. A belief-aware leaf therefore needs a design decision (whose belief a
leaf carries, in the spirit of the paper's knowledge-limited subgame solving) plus synchronous expansion across
roots, not an adapter. It stays the prerequisite for a ReBeL-style loop that uses the belief at the frontier.

### 4.2 Label fallbacks and bias
9.7 % of label moves fell back, almost all during first-ply construction at SF-d8 speed, biased against wide
positions. Remedies: a cheaper leaf (the network), a longer clock, or pruned construction with a move prior.

### 4.3 Memory
Two exact trackers in one 8000m container are killed on long games; one exact tracker peaks at 1-3 GB but a
single update on a 200-ply game took 371 s. The guard tracker bounds both. The VM has 15 GB: one 8000m
container at a time, or one 8000m plus one 4000m training container (`torch4g.sh`).

### 4.4 Single-run noise
Position error moves +-0.015 between seeds of one recipe. Any claim about a difference smaller than that needs
three seeds per arm.

### 4.5 Resumed Atlas tasks exit 1
The in-run validator compares the parts with the first run's `manifest.json`; the rewritten manifest is
consistent. Harmless; fix by validating after writing the manifest.

in `/home/dev/cs5446-review/labels/tools/` and `/home/dev/cs5446-review/experiment/`; the scripts contain
those absolute paths.

1. **Labels on Atlas** (`$EXP/atlas/`): `qsub -J 1-20 -v TAG=labels-sf8-r3,GAMES=12,BUDGET_MS=30000,MAX_STATES=96000,SEED_BASE=80001 label_sf8b.pbs`
   from `/hpctmp/tommy.21.31/fow`. Progress: `wc -l repo-exp/pair_c/runs/<TAG>/task-*/progress.jsonl`.
   A dead task resumes with the same command plus `N=<task>` and no `-J`; clear engine-dead placeholders first
   with `clear_dead_engine_games.py`. Statistics: `label_stats.py`.
2. **Pull and merge** (`$EXP/pipeline/`): `pull_final.sh <name>` (laptop: rsync Atlas -> laptop -> VM, keeps only
   games with a progress row, starts the chain); on the VM `merge_labels.py <dst> <task dirs>`,
   `validate_labels.py --require-played-policy`.
3. **Baselines**: `baseline_leaf.py <dataset> val --stockfish /usr/games/stockfish --depths 1,8`.
4. **Train / evaluate**: `train_belief_net.py --data <dataset> --out <run> --lr 1e-3 [--input marginals|observation]
   [--no-context] [--policy-weight W] --device cuda --workers 6 --cache-dir <cache>`;
   `eval_belief_net.py --run <run> --data <dataset> --split val`. Inside the container: `torch.sh` (8000m) or
   `torch4g.sh` (4000m). Chains: `final_chain.sh`, `ablation_chain.sh`, `gen_sweep.sh`.
5. **Paired comparison of runs**: `compare_runs.py --data <dataset> --runs <reference> <others...> [--leaf-mode]`.
6. **Strength arms** (`$EXP/strength/`): `launch_netv2_arms.sh <run name> 50` copies the checkpoint, writes the
   ini files (`make_netv2_inis.py`, templates from the earlier arms) and starts `run_arm_gpu.sh` (LIMIT from the
   environment); `netv2_scores.py` for scores; `switch_arms.sh` to change the arm set without losing finished
   chunks. One `fow-` container at a time.

7. **Play the network v2 leaf in Fog Lab.** Fog Lab (Pair B's `pairb.lab`) offers Pair A's subgame agent as a bot
   and lets the New game panel choose the bot's leaf from the scorer list. This branch adds the scorer
   `belief-v2` ("Belief network v2 (solver labels, engine-free)"), which loads `pair_b/checkpoints/belief-solver-v2-sf8-g237/best.pt`
   and needs no Stockfish. Start the lab with the GPU: `$EXP/pipeline/foglab_up_gpu.sh` on the VM (port 8777), then
   from the laptop `ssh -N -L 8765:127.0.0.1:8777 homelab` and open `http://127.0.0.1:8765`; pick bot "Pair A
   subgame agent" and scorer "Belief network v2". The bot plays at 5 s per move with the 96,000-state guard tracker,
   exactly the configuration of the `netv2-vs-fe-guard-s16` arm's network side. Note that the search still hands
   the network one board at a time (section 4.1).

Never read the test split except once, at the very end, with `--final`.

## 6. Open work, in the order recommended

1. Finish and read the arms: `netv2-fe-s16` and `netv2-vs-fe-guard-s16` to 100 games each (about two days at
   65 min per head-to-head chunk). The head-to-head result decides whether the network leaf is worth more work.
2. Round 3 -> `solver-v2-sf8-480`, recipe v2, three seeds: the next learning-curve point.
3. Profile: done, section 2.9. The solver's Python traversal is the bottleneck, not the leaf.
4. **The native port**, decided 2026-11-10 for the continuation after the course, in the order the profile sets:
   A) the PCFR+ round as a native kernel on an array-based tree rebuilt once per growth step (regrets and
   strategies in arrays, the recursive traversal as an iterative loop), about 2x; B) fog-chess rules and move
   generation native with Python bindings, replacing python-chess in construction and growth, 1.3-1.5x more;
   C) construction across cores; D) growth sampler, projection and gadgets native, the full loop, where 10x and
   beyond lives. Each phase behind a flag with the Python path kept as the reference and equivalence tests on
   recorded positions (`profile_move.py` shows how to replay a record). The tracker's native backend is the model.
5. Depth-cap experiment after phase A: `max_depth` 4 and 6 with the network leaf; nodes, depth reached, rounds,
   fallbacks.
6. The belief-aware leaf (section 4.1): decide whose belief a frontier board carries, expand information sets
   synchronously across roots, test one-board groups for equivalence, then one arm.
7. Three seeds per arm for every offline comparison that goes into the report; one test-split evaluation at the end.
8. Only after 6: self-play iterations with the network as the labelling leaf (`label_run.py` needs a
   `belief_network` evaluator option; the factory already supports it), a 5 s clock, random root moves at a small
   rate for exploration, outcome-mixed value targets, the SF-d8-labelled validation games as the fixed yardstick.
9. Policy head: have the runner write the solver's average strategy and per-move root values, then revisit.
10. Repository: the search-node figure in the 2026-11-08 handover on main ("218 nodes") is wrong, the measured
    median is about 1,370; open pull requests #66/#67 await fixes; Pair B asked for data and checkpoint hashes,
